# Issue tracker: GitHub

Issues and specs for this repo live as issues on `https://github.com/osamahaltassan/lazyfin`. Use the `gh` CLI, already logged in on the maintainer's Mac, for every operation, and `gh api` for any endpoint `gh` has no command for. Inside the clone, `gh` infers the repo, and `gh api` fills `{owner}` and `{repo}`.

## Conventions

- **Create an issue**: `gh issue create --title "..." --body-file <file> --label "..."`. Write multi-line bodies to a file first.
- **Read an issue**: `gh issue view <number> --comments` for a readable view, or `gh issue view <number> --json number,title,body,labels,assignees,comments` for JSON.
- **List issues**: `gh issue list --state open --json number,title,labels,assignees` with `--state`, `--label`, `--assignee`, and `--search` filters.
- **Edit the body**: `gh issue edit <number> --body-file <file>`.
- **Comment on an issue**: `gh issue comment <number> --body "..."`.
- **Apply / remove labels**: `gh issue edit <number> --add-label "..."` / `--remove-label "..."`.
- **Assign**: `gh issue edit <number> --add-assignee @me`.
- **Close**: `gh issue close <number> --comment "..."`.
- **Pin**: `gh issue pin <number>`. List pinned issues with `gh api graphql -f query='query{repository(owner:"osamahaltassan",name:"lazyfin"){pinnedIssues(first:3){nodes{issue{number title url}}}}}'`. GitHub allows three pinned issues per repo, and `Order of work` holds one of them.

Agent-written issues start with the line `> *This was generated by AI during a <skill> session.*` so a reader knows the author.

## Pull requests as a triage surface

**PRs as a request surface: no.** _(Set to `yes` if this repo treats external PRs as feature requests; `/triage` reads this flag.)_

When set to `yes`, PRs run through the same labels and states as issues, using the `gh pr` equivalents:

- **Read a PR**: `gh pr view <number> --comments` and `gh pr diff <number>` for the diff.
- **List external PRs for triage**: `gh api --paginate 'repos/{owner}/{repo}/pulls?state=open' --jq '.[] | select(.author_association | IN("OWNER","MEMBER","COLLABORATOR") | not) | {number, title, author: .user.login, author_association, labels: [.labels[].name]}'`.
- **Comment / label / close**: `gh pr comment`, `gh pr edit --add-label`/`--remove-label`, `gh pr close`.

GitHub shares one number space across issues and pull requests, so a bare `#42` may be either: `gh pr view 42` falls back to `gh issue view 42`.

## Wayfinding operations

Used by `/wayfinder`. The **map** is a single issue with **child** issues as tickets.

- **Map**: a single issue labelled `wayfinder:map`, holding the Destination / Notes / Decisions-so-far / Not-yet-specified / Out-of-scope body.
- **Child ticket**: a GitHub sub-issue of the map, created with `gh issue create --parent <map> ...` or attached later with `gh issue edit <map> --add-sub-issue <child>`. Its body starts with `Part of #<map> — [<map title>](<map url>).` and the AI line. Labels: exactly one `wayfinder:<type>` (`research`/`prototype`/`grilling`/`task`) and nothing else. The map body lists its open children under a `## Tickets` heading in build order.
- **Blocking**: GitHub's **native issue dependencies**, visible in the issue's sidebar. Add an edge with `gh api -X POST repos/{owner}/{repo}/issues/<child>/dependencies/blocked_by -F issue_id=<blocker-db-id>`, where `<blocker-db-id>` is the blocker's database id from `gh api repos/{owner}/{repo}/issues/<blocker> --jq .id`, never its `#number`. List a ticket's open blockers with `gh api repos/{owner}/{repo}/issues/<child>/dependencies/blocked_by`. A ticket is unblocked when every blocker is closed.
- **Frontier query**: list the map's open children, drop any with an open blocker or an assignee; first in the map's `## Tickets` order wins.
- **Claim**: `gh issue edit <number> --add-assignee @me`, the session's first write.
- **Resolve**: `gh issue comment <number> --body "<answer>"`, then `gh issue close <number>`, then append a context pointer (gist + link) to the map's Decisions-so-far and remove the ticket from its `## Tickets` list.

## Order of work

`Order of work` is one issue, pinned, always open, even when it lists nothing. It shows the maintainer what gets built before what, across every map and standalone issue in the repo.

Its body has these sections, in this order, and an empty section says `None.`:

- **Maps**: every open wayfinder map, in build order. Under each map, its open tickets in the map's own order, with their `wayfinder:` type.
- **Standalone issues**: every open issue that belongs to no map, in build order.
- **Later**: open issues the maintainer has set aside on purpose, with one line each on what they wait for.

Each entry is the issue's title linking to it, never a bare number. A closed issue leaves the list; a new one enters it in its place in the order; a map's tickets move with the map.

The body keeps this shape, with one numbering that runs through maps and their indented tickets:

```markdown
> *This was generated by AI during a <skill> session.*

The build order across this repo. Whoever opens, closes, or reorders an issue updates this list. Within a map, the map's own ticket order applies.

## Maps

1. [<map title>](<map url>)
   2. [<ticket title>](<ticket url>): <wayfinder type>

## Standalone issues

None.

## Later

None.
```

The agent updates `Order of work` in the same operation as the change that made it stale: opening or closing an issue or ticket, charting or closing a map, or the maintainer reordering work. Done when every open map, ticket, and standalone issue in the tracker appears exactly once and the order matches the maintainer's.

Create it with `gh issue create --title "Order of work" --body-file <file>`, pin it with `gh issue pin <number>`, and find it in the pinned-issues query under **Pin**.
