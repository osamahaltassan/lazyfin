## Question

Can a plugin tell which client sent a request, from the `Authorization` header's client name and device ID or anything else, reliably enough to aim a change at Jellyfin Web clients only, or at native clients only?

## Short answers

- **Yes, by exact client name, for every official client but one.** The server reads `Client`, `Device`, `DeviceId`, and `Version` from the `Authorization: MediaBrowser ...` header of every request and puts them on the request's claims. Every official client sends a fixed `Client` name, and the name tells Jellyfin Web apart from native clients, with one exception below.
- **Jellyfin Web does not always call itself "Jellyfin Web".** In a browser it does. Inside an official app, the app's NativeShell replaces the name: `Jellyfin iOS` or `Jellyfin iPadOS`, `Jellyfin for Android`, `Jellyfin Desktop`, `Jellyfin for WebOS`, `jellyfin-uwp` (Xbox), and `Jellyfin for Tizen`. So "Jellyfin Web clients" is a list of seven names, not one.
- **The Android app is the exception.** Its Jellyfin Web pages and its native player send the same `Client` (`Jellyfin for Android`) and the same `DeviceId`. Only the `User-Agent` separates them: the web view sends Android WebView's default browser string, and the native player's API calls send `Jellyfin for Android/<version> via jellyfin-sdk-kotlin (OkHttp/...)`.
- **Match names exactly, never by prefix.** Jellyfin Vue, a separate web app that never runs Jellyfin Web, calls itself `Jellyfin Web (Vue)`. A "starts with Jellyfin Web" rule would catch it.
- **Any client can claim any name.** The header's `Client` and `DeviceId` win over what the access token was issued to, and the server never checks them against each other. So the client name is good for aiming a user-experience change, and useless for anything that grants access or hides data.
- **Unknown clients must get Jellyfin's normal answer.** Third-party clients pick their own names, and new official ones appear. A change aimed at "native clients" should use a list of known native names, not "everything that is not Jellyfin Web", or decide on purpose that unknown clients count as native.
- **User-Agent, Referer, and session info add little.** `User-Agent` is free text that differs by browser, web view, and platform; it helps only for the Android split above. Jellyfin Web sets `no-referrer`, so no `Referer` is sent. The session the server keeps is built from the same header values. The route itself tells nothing: Jellyfin Web and native clients call the same API endpoints.

## Part 1: what the server reads

### Parsing the header

`AuthorizationContext.GetAuthorizationDictionary` reads the `Authorization` header. Only when `EnableLegacyAuthorization` is on does it fall back to `X-Emby-Authorization` (`Jellyfin.Server.Implementations/Security/AuthorizationContext.cs:229-239`). The scheme must be `MediaBrowser`; `Emby` is accepted only with legacy authorization on (`:246-264`). The rest is split on commas outside quotes into `key=value` pairs, each value trimmed of quotes and URL-decoded (`:276-317`). Keys are case-sensitive, because the dictionary uses the default comparer (`:278`).

`EnableLegacyAuthorization` defaults to `false` (`MediaBrowser.Model/Configuration/ServerConfiguration.cs:290`), and the migration `DisableLegacyAuthorization` turns it off on upgrade (`Jellyfin.Server/Migrations/Routines/20260531160000_DisableLegacyAuthorization.cs:25-30`). That migration is in every 12.x tag (`git tag --contains a6ae68433a` lists `v12.0` to `v12.3`). So on a default 12.x or 13.0 server, only `Authorization: MediaBrowser ...` carries client identity.

Of the pairs, the server keeps five: `DeviceId`, `Device`, `Client`, `Version`, and `Token` (`AuthorizationContext.cs:84-91`). Any other key, such as Roku's `UserId`, is ignored. The token can also come from the `ApiKey` query parameter, and with legacy authorization on, from `X-Emby-Token`, `X-MediaBrowser-Token`, or `api_key` (`:93-111`). Client identity never comes from the query string.

### Header values win over the token's device

When the request has a token, the server looks up the device record the token was issued to (`:132-133`). It fills `Client` and `DeviceId` from that record only when the header left them empty (`:141-149`). When the header's `Device` or `Version` differs from the record, it overwrites the record (`:154-178`). It never compares the header's `Client` or `DeviceId` with the record.

The device record itself is written at login from the same header: `AuthenticateUserByName` passes `auth.Client`, `auth.DeviceId`, and `auth.Device` into `AuthenticateNewSession` (`Jellyfin.Api/Controllers/UserController.cs:214-223`), which stores them with the new token (`Emby.Server.Implementations/Session/SessionManager.cs:1762`, `:1810`).

So a request's client name is whatever the request says, and, only when it says nothing, whatever the login request said. Jellyfin's own code confirms this: the session key includes the user ID "because the client name and the device id are taken from the request headers and are not bound to the access token" (`Emby.Server.Implementations/Session/SessionManager.cs:478-482`).

An API key request gets `Client` set to the key's name, and the server's own name and ID as device (`AuthorizationContext.cs:195-216`).

### Where a plugin reads it

- **After authentication, from claims.** `CustomAuthenticationHandler` copies the parsed values into claims named `Jellyfin-Client`, `Jellyfin-DeviceId`, `Jellyfin-Device`, and `Jellyfin-Version` (`Jellyfin.Api/Auth/CustomAuthenticationHandler.cs:60-71`, names at `Jellyfin.Api/Constants/InternalClaimTypes.cs:16-31`). A global MVC filter, the server-route way LAZ-61 recommends, reads them from `HttpContext.User` with no database call. `Jellyfin.Api` is not a NuGet package, so Lazyfin cannot use `ClaimsPrincipalExtensions.GetClient()` and must read the claim by its string name. A test per supported server version should check the names still match.
- **Without a token, from `IAuthorizationContext`.** A request with no token, such as the login call or `/System/Info/Public`, gets no claims (`CustomAuthenticationHandler.cs:48-51`). `IAuthorizationContext.GetAuthorizationInfo(HttpRequest)` (`MediaBrowser.Controller/Net/IAuthorizationContext.cs:23`) parses the header for any request. It lives in `MediaBrowser.Controller`, which Lazyfin already compiles against. When a token is present, it also looks up the device and may write to the database (`AuthorizationContext.cs:129-191`), so a filter should prefer the claims and call this only when there are none.
- **The session.** Jellyfin keeps a `SessionInfo` per user, client name, and device ID, filled from the same claims (`Jellyfin.Api/Helpers/RequestHelpers.cs:132-138`, `Emby.Server.Implementations/Session/SessionManager.cs:494-533`). It adds no new evidence about which app is calling.

### What else the server sees

- **The route.** Jellyfin Web and native clients call the same API endpoints, as `research/client-reach.md` shows for Next Up, Resume, Latest, and PlaybackInfo. Only Jellyfin Web loads `/web/...` static files, and only legacy clients such as Roku and JellyCon use the legacy `Users/{userId}/...` routes, but neither tells who sends a given API call.
- **`User-Agent`.** The server reads it only to pick image formats and to key transcodes (`Jellyfin.Api/Controllers/ImageController.cs:1957`, `Jellyfin.Api/Helpers/StreamingHelpers.cs:81`, `:379`). It is free text set by each browser, web view, or HTTP library.
- **`Referer`.** Jellyfin Web's page sets `<meta name="referrer" content="no-referrer">` (`jellyfin-web:src/index.html:14`), so its requests carry no `Referer`.
- **Requests without the header.** Jellyfin Web puts the token in the `ApiKey` query parameter for URLs a media element or the subtitle renderer fetches, such as audio streams (`jellyfin-web:src/components/playback/playbackmanager.js:323`) and fallback fonts (`jellyfin-web:src/plugins/htmlVideoPlayer/plugin.js:1392-1394`). Those requests get `Client` from the device record, which is the name Jellyfin Web logged in with. An anonymous image request has no identity at all.

## Part 2: what each official client sends

### Jellyfin Web, and the apps that run it

Jellyfin Web asks `appHost` for its identity and passes it to both API clients it uses (`jellyfin-web:src/lib/jellyfin-apiclient/ServerConnections.js:63-69`, `:152-158`). `appHost` returns the NativeShell's value when an app supplies one, and its own otherwise (`jellyfin-web:src/components/apphost.js:387-402`). Its own values are `Jellyfin Web` as `Client` (`:11`), the Jellyfin Web package version, a browser name such as `Chrome` or `Firefox` with ` iPhone`, ` iPad`, or ` Android` added (`:152-174`), and a device ID kept in `localStorage` under `_deviceId2`, made from the `User-Agent` and the time (`:125-150`). The legacy client writes them as `Authorization: MediaBrowser Client="...", Device="...", DeviceId="...", Version="...", Token="..."` (`jellyfin-apiclient:src/apiClient.js:166-196`). The newer SDK writes the same fields URL-encoded (`jellyfin-sdk-typescript:src/utils/authentication.ts:11-19`).

## Part 3: can a client pass for another?

Yes, freely. Nothing in the header is signed, and the server takes the header's `Client` and `DeviceId` over the token's device record (Part 1). A browser extension, a third-party app, or a script can send `Client="Jellyfin Web"` or `Client="Swiftfin tvOS"`. Even the official apps mix: the Android app's native player sends the same name as its Jellyfin Web pages.

What that means for Lazyfin:

- **Fine for user-experience changes.** If a client lies about its name, the only one hurt is that client, which gets a change meant for another. Lazyfin's enhancements are of that kind.
- **Never for access.** A change that shows, hides, or allows something based on the client name is bypassed by changing one header. That is also true of Jellyfin's own code, which uses the name only for sessions, logs, and display.

## Part 4: how a server-route change can aim at one kind of client

A Lazyfin filter can classify a request like this, in order:

1. Read `Jellyfin-Client` from the claims, or from `IAuthorizationContext` when there are none.
2. If it is exactly one of `Jellyfin Web`, `Jellyfin iOS`, `Jellyfin iPadOS`, `Jellyfin Desktop`, `Jellyfin for WebOS`, `jellyfin-uwp`, or `Jellyfin for Tizen`, the request comes from Jellyfin Web.
3. If it is exactly `Jellyfin for Android`, check the `User-Agent`: one that contains `via jellyfin-sdk-kotlin` or `AndroidXMedia3` is the native side; anything else is the web view running Jellyfin Web.
4. If it is one of the native names in Part 2, the request comes from a native client.
5. Anything else is unknown: leave the request and response as Jellyfin made them, unless the enhancement decides on purpose how unknown clients are treated.

How this breaks:

- **Renamed clients.** A client that changes its name falls into "unknown" and silently loses the change. The names have been stable in source, but nothing promises it. A list per supported version, with a test, keeps this visible.
- **Third-party wrappers.** A third-party app that wraps Jellyfin Web under its own name looks unknown. A third-party native app that sends `Jellyfin Web` gets Jellyfin Web's treatment.
- **The iPad name.** The iPhone/iPad app's name depends on the OS name iOS reports, so both `Jellyfin iOS` and `Jellyfin iPadOS` must be listed.

## For the map

Facts the map could use:

- **A change through the Jellyfin Web route reaches the same viewers that steps 2 and 3 above pick out**, except Tizen's bundled copy. So a server-route change aimed at "native clients only" can be the server-side twin of a Jellyfin Web route change without the two overlapping, as long as unknown clients get neither or both on purpose.
- **A signal Lazyfin sets itself would be firmer than client names.** The Lazyfin script that LAZ-65 loads into Jellyfin Web runs in every Jellyfin Web client it reaches, whatever app wraps it. It could tell the server which device IDs run it, or tag the requests it cares about. That would not fix Android's shared device ID, and it leans on Jellyfin Web internals, so it is an option for LAZ-62 or LAZ-65 to weigh, not a recommendation here.
- **WebSocket identity.** A browser cannot set headers on a WebSocket, so `jellyfin-apiclient` 1.11.0 opens it with `?api_key=<token>&deviceId=<id>` (`jellyfin-apiclient:src/apiClient.js:613-627`), and the server takes the client name from the token's device record (`Emby.Server.Implementations/HttpServer/WebSocketManager.cs:40`). Read as written, the server accepts `api_key` only with legacy authorization on (`AuthorizationContext.cs:108-111`). This was not run, and it does not change the answer above, but it matters to whoever picks up the map's WebSocket question.
