## 1. Registration order, and who resolves the concrete types

## 3. How burn-in builds the subtitle filter

`GetTextSubtitlesFilter` is at `v12.0:MediaBrowser.Controller/MediaEncoding/EncodingHelper.cs:1924`, and at `:1943` on `v12.3` and `master`. Its body is unchanged; the 19-line shift comes from encoder-option changes earlier in the file.

For an **external** subtitle file (`v12.0:…:1944-1971`, `v12.3`/`master`: `…:1963-1990`):

- it asks `ISubtitleEncoder.GetSubtitleFileCharacterSet` for the charset, only when the stream has a language (`v12.0:…:1948-1960`, `v12.3`/`master`: `…:1967-1979`),
- it adds `":charenc=" + charenc` when the answer is not empty (`v12.0:…:1958`, `v12.3`/`master`: `…:1977`),
- it formats `"subtitles=f='{0}'{1}{2}{3}{4}{5}"` with `_mediaEncoder.EscapeSubtitleFilterPath(state.SubtitleStream.Path)` first and the charset option second (`v12.0:…:1964-1965`, `v12.3`/`master`: `…:1983-1984`).

For an **embedded** subtitle (`v12.0:…:1973-1985`, `v12.3`/`master`: `…:1992-2004`):

- it gets the extracted file from `ISubtitleEncoder.GetSubtitleFilePath` (`v12.0:…:1973`, `v12.3`/`master`: `…:1992`),
- it formats `"subtitles=f='{0}'{1}{2}{3}{4}"` with `_mediaEncoder.EscapeSubtitleFilterPath(subtitlePath)` and no charset option (`v12.0:…:1980-1981`, `v12.3`/`master`: `…:1999-2000`).

The other options follow the path in both forms: `:alpha=1`, `:sub2video=1`, `:fontsdir='…'`, and `,setpts=PTS -N/TB` for progressive streams.

`IMediaEncoder.EscapeSubtitleFilterPath(string path)` is declared at `MediaBrowser.Controller/MediaEncoding/IMediaEncoder.cs:240` at all three refs. The implementation is identical at `v12.0:MediaBrowser.MediaEncoding/Encoder/MediaEncoder.cs:1215` and `v12.3`/`master`: `…/MediaEncoder.cs:1224`. It turns `\` into `/`, then escapes `:` as `\:`, `'` as `'\\\''`, and `"` as `\"`.

**Answer: same filter, same `:charenc=` rule, same escaping. Yes for 12.0, 12.3, and 13.0.**

Two facts here shape the burn-in ticket ([#9](https://github.com/osamahaltassan/lazyfin/issues/9)):

1. **Embedded subtitles reach the filter through `ISubtitleEncoder.GetSubtitleFilePath`.** The `ISubtitleEncoder` decorator could hand burn-in the fixed copy for embedded tracks on its own. External files skip `ISubtitleEncoder` for the path, so they still need the `StartFfMpeg` rewrite. Doing both in `StartFfMpeg` keeps burn-in in one place; returning the copy from `GetSubtitleFilePath` would also change what the 12.3 and 13.0 image-subtitle path sees, so it must stay limited to text subtitles if it is ever used.
2. **The `:charenc=` option must go when the path is swapped.** For an external file with a language, the filter says, for example, `subtitles=f='/media/a.ar.srt':charenc=CP1256`. Lazyfin's copy is UTF-8, so leaving `:charenc=CP1256` makes ffmpeg decode UTF-8 bytes as Windows-1256 and burn in garbage. The rewrite must replace `subtitles=f='<escaped original>'` followed by an optional `:charenc=<value>` with `subtitles=f='<escaped copy>'`. The decorator can build the exact original text with the injected `IMediaEncoder.EscapeSubtitleFilterPath`, because the decorator receives the same `StreamState` the command was built from.

## 4. Building the original implementation

### Can the plugin see `MediaBrowser.MediaEncoding` at runtime?

Yes, as `Type` objects, without referencing the assembly.

- The server loads `MediaBrowser.MediaEncoding` into the default load context. `ApplicationHost.cs:567` names `MediaBrowser.MediaEncoding.Encoder.MediaEncoder` directly, and `ApplicationHost.cs:907` adds that assembly to the composable parts.
- Each plugin gets its own collectible `PluginLoadContext` (`PluginManager.cs:130-140`, `PluginLoadContext.cs:17`). Its `Load` override returns an assembly only when the plugin's `AssemblyDependencyResolver` finds it, and returns `null` otherwise (`PluginLoadContext.cs:23-31`). A `null` makes the runtime fall back to the default context, so the plugin shares the server's `MediaBrowser.Controller`, `MediaBrowser.Model`, and `Microsoft.Extensions.DependencyInjection.Abstractions`, and therefore the same `ISubtitleEncoder` and `ITranscodeManager` types.
- The descriptor at `ApplicationHost.cs:625` is `ServiceDescriptor(typeof(ISubtitleEncoder), typeof(SubtitleEncoder), Singleton)`. Its `ImplementationType` is the default context's `SubtitleEncoder`, and the plugin can hand that `Type` to the container or to `ActivatorUtilities` with no compile-time reference.

Two load conditions follow:

- **The plugin zip must not ship any server assembly** (`MediaBrowser.*.dll`, `Jellyfin.*.dll` from the server, `Microsoft.Extensions.DependencyInjection*.dll`). If the resolver finds a copy in the plugin folder, the plugin loads its own `ISubtitleEncoder` type, which is not the server's, and the descriptor lookup finds nothing. Reference `Jellyfin.Controller` with `<ExcludeAssets>runtime</ExcludeAssets>` and check the built output.
- **`targetAbi` in the manifest must be `12.0.0.0` or lower.** `PluginManager.cs:745-755` loads the plugin as supported only when `_appVersion >= targetAbi`. A plugin compiled against assembly version 12.0.0.0 binds to the 12.3.0.0 or 13.0.0.0 server assembly through the default context, because a higher version satisfies the reference.

### The two lifetime risks

**`TranscodeManager` has side effects in its constructor** (`TranscodeManager.cs:70-97`). It calls `DeleteEncodedMediaCache()` (`:94`, body at `:718`), which empties the transcode folder, and subscribes to `ISessionManager.PlaybackProgress` and `PlaybackStart` (`:95-96`). Imagine the decorator builds a fresh inner `TranscodeManager` and something else also builds the original one. The second constructor wipes the transcode folder while the first one is streaming from it, and both instances react to every playback event. So **exactly one inner instance must ever exist**, and it must be a singleton. A factory that calls `ActivatorUtilities.CreateInstance` is safe only if the decorator itself is a singleton, which it is when it keeps the original lifetime. Never register the inner type in a way that lets it be built twice, and do not keep the core descriptor in the collection, where `GetServices<ITranscodeManager>()` would build a second one.

**Both classes are `IDisposable`.** `TranscodeManager.Dispose` unsubscribes the events and disposes its lock pool (`TranscodeManager.cs:752-757`); `SubtitleEncoder.Dispose` disposes its lock pool (`v12.0:…/SubtitleEncoder.cs:1040-1043`). The container disposes only the objects it creates. An inner built by `ActivatorUtilities.CreateInstance` inside a factory is created by the plugin, so the container never disposes it. That leak only matters at shutdown, but it is avoidable.

### Recommended registration

Let the container build and own the inner object, under its own concrete type, and register the decorator as a factory for the interface with the original lifetime:

```csharp
public sealed class PluginServiceRegistrator : IPluginServiceRegistrator
{
    public void RegisterServices(IServiceCollection serviceCollection, IServerApplicationHost applicationHost)
    {
        var subtitleEncoder = FindCore<ISubtitleEncoder>(serviceCollection);
        var transcodeManager = FindCore<ITranscodeManager>(serviceCollection);

        Decorate<ISubtitleEncoder>(serviceCollection, subtitleEncoder,
            (provider, inner) => ActivatorUtilities.CreateInstance<RtlSubtitleEncoder>(provider, inner));
        Decorate<ITranscodeManager>(serviceCollection, transcodeManager,
            (provider, inner) => ActivatorUtilities.CreateInstance<RtlTranscodeManager>(provider, inner));
    }

    private static ServiceDescriptor FindCore<TService>(IServiceCollection services)
        => services.LastOrDefault(d => d.ServiceType == typeof(TService) && !d.IsKeyedService)
           ?? throw new InvalidOperationException($"No {typeof(TService).Name} registration to decorate.");

    private static void Decorate<TService>(
        IServiceCollection services,
        ServiceDescriptor original,
        Func<IServiceProvider, TService, TService> decorate)
        where TService : class
    {
        Func<IServiceProvider, TService> inner = original switch
        {
            { ImplementationType: { } type } => provider => (TService)provider.GetRequiredService(type),
            { ImplementationFactory: { } factory } => provider => (TService)factory(provider),
            { ImplementationInstance: { } instance } => _ => (TService)instance,
            _ => throw new InvalidOperationException($"Cannot decorate {typeof(TService).Name}."),
        };

        services.Remove(original);
        if (original.ImplementationType is { } implementationType)
        {
            services.Add(new ServiceDescriptor(implementationType, implementationType, original.Lifetime));
        }

        services.Add(new ServiceDescriptor(
            typeof(TService),
            provider => decorate(provider, inner(provider)),
            original.Lifetime));
    }
}
```

Why this shape:

- **The container owns the inner object.** Registering `SubtitleEncoder` and `TranscodeManager` as themselves, singleton, means the container builds each once and disposes each at shutdown. The decorators should not implement `IDisposable` and should not dispose the inner, or the inner is disposed twice.
- **Remove, then add.** `services.Remove(original)` takes the core descriptor out, so `GetServices<T>()` cannot build a second `TranscodeManager`. `ServiceCollectionDescriptorExtensions.Replace` would also work, but it removes the first descriptor of the service type, which is the wrong one if another plugin registered after the core.
- **Look up both descriptors before changing anything.** If `RegisterServices` throws, `PluginManager.cs:229-235` marks Lazyfin `Malfunctioned`, but any change already made to the collection stays. Failing before the first change leaves the server with its own services intact.
- **Skip keyed descriptors.** In Microsoft DI 8 and later, reading `ImplementationType` on a keyed descriptor throws. The core registrations are not keyed, but the filter keeps the lookup safe.
- **Handle a factory or an instance too.** If another plugin decorated the same service first, the last descriptor is that plugin's factory. Wrapping it chains the two decorators instead of dropping the other plugin's.
- **`ActivatorUtilities` builds only the decorator,** so the decorator can take any other server service (`IMediaEncoder`, `IApplicationPaths`, `ILogger<T>`) in its constructor next to the inner.

The decorators forward every member to the inner and change only `ISubtitleEncoder.GetSubtitles` and `ITranscodeManager.StartFfMpeg`. Neither inner class uses the other's decorator in a way that creates a cycle: `EncodingHelper` takes `ISubtitleEncoder` and `TranscodeManager` takes `EncodingHelper`, so the transcode path already goes through the subtitle decorator, as it should.

## Risks that could change the plan

1. **Burn-in charset.** The `StartFfMpeg` rewrite must drop `:charenc=…` along with the path, or burn-in of non-UTF-8 external files breaks (section 3).
2. **One `TranscodeManager` only.** A second instance wipes the transcode folder mid-stream (section 4).
3. **No server assemblies in the plugin zip,** or the decorator silently never applies (section 4).
4. **A future interface member disables the whole plugin** through `GetTypes()` at load (section 2). Nothing in 12.3 or `master` does that today; re-check `ISubtitleEncoder.cs` and `ITranscodeManager.cs` before each server release Lazyfin claims to support.
5. **Embedded burn-in has a second hook.** `GetSubtitleFilePath` feeds embedded burn-in and, from 12.3, image-subtitle delivery. Keep the decorator's override of it a pass-through unless the burn-in ticket decides otherwise (section 3).
