## 3. Conventions for the pull request

### Title and commits

- Title: short, imperative, capitalized, no closing punctuation. It becomes the changelog entry, and the core team may edit it (`development.md`, Pull Request Guidelines; the template's header comment).
- No Conventional Commits in titles or commit messages (`master:CONTRIBUTING.md`, Pull Requests).
- Commit messages follow chris.beams.io "How to Write a Git Commit Message". Squash "junk" commits, but keep one commit per significant change. Recent `master` subjects look like "Fix player source removal" and "Remove Hls global".
- Do not rebase once reviews start, and do not merge `master` in unless there are conflicts (`master:CONTRIBUTING.md`; `development.md`).
- One focus per pull request; no unrelated refactoring (`master:CONTRIBUTING.md`; LLM policy rule 1).
- Two team member reviews are needed to merge to `master` (`development.md`).

### Target branch

Maintainers ask bug fix pull requests on `master` to rebase onto `release-12.z` and retarget, then label them `stable backport`. Examples: 8558 and 8564 (theguymadmax: "Please retarget and rebase this to the current stable branch (release-12.z)"), 8570 (dmitrylyzo, pointing at `CONTRIBUTING.md`), 8644 (dkanada: "rebase this branch against `release-12.z` and we'll merge it sooner"). The steps are in `master:CONTRIBUTING.md`, "Targeting a Release Branch". The fix's code is the same on both branches, so either base works; `release-12.z` saves a round trip.

### The template, section by section

From `master:.github/PULL_REQUEST_TEMPLATE.md` (last changed 2026-09-18, commit `f75f7016`):

- **Header comment**: title short, descriptive, imperative ("Fix X", not "Fixed X").
- **### Changes**: 1 to 5 sentences. Before and after screenshots for UI changes.
- **### Issues**: tag the issues it solves, such as `Fixes #8725`.
- **### Code assistance**: say whether AI was used. "List the exact tool, model, and version used and the specific actions that it performed." Example given: "all code generated by Gemma 4; investigated by LLama 4 Scout". "Do NOT editorialize on code ownership, confidence, or any other aspect of LLM usage." Accepted examples: 8722 wrote "Zed autocomplete"; 8396 named Claude Code and what it did.
- **Checklist** of four boxes: read and followed the contributing guidelines; tested the changes; checked it does not duplicate an existing pull request; gave a *substantive* review of another web pull request.
- An incomplete template "will result in the PR being closed as invalid without review" (`master:CONTRIBUTING.md`).

### What the LLM policy expects

From `llm-policies.md`:

- No LLM output in pull request bodies or comments. The body must be the author's own words and explain what changed and why. Breaking this means closure (General Guidelines 1; Code Contributions 3).
- "Pure vibe coding will be rejected." The author must review the output, explain it, and handle review feedback without pasting it back into an LLM (2, 3, 5).
- Concise and focused; large changes split into small commits (1).
- No excess comments, no spaces on empty lines, no LLM metafiles such as `.claude` (2).
- Tested, including the changed behaviour itself (4).
- Reviewers have final say; a hard-to-review pull request is asked to split (7).
