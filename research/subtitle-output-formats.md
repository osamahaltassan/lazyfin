## How a subtitle reaches a client

`ISubtitleEncoder.GetSubtitles` has one caller, `SubtitleController.GetSubtitle` (`v12.3:Jellyfin.Api/Controllers/SubtitleController.cs:520`). The route is `Videos/{id}/{mediaSourceId}/Subtitles/{index}[/{startTicks}]/Stream.{format}`, and the format `js` becomes `json` before the call (`SubtitleController.cs:231-234`). Image formats (`pgssub`, VobSub) are served from disk and never reach the encoder (`SubtitleController.cs:240-247`).

Inside `GetSubtitles` (`v12.3:MediaBrowser.MediaEncoding/Subtitles/SubtitleEncoder.cs:119-153`):

1. `GetReadableFile` picks the file and its format (`SubtitleEncoder.cs:211-275`).
   - An embedded track is first extracted by ffmpeg to the subtitle cache. ASS and SSA keep their codec; every other embedded text codec (subrip, webvtt, mov_text, ...) becomes `.srt` (`SubtitleEncoder.cs:476-492`, `:681`). So an embedded track always arrives as `srt`, `ass`, or `ssa`.
   - An external file keeps its extension as its format (`SubtitleEncoder.cs:235`, `:268-274`). The library only picks up `.ass .mks .sami .smi .srt .ssa .sub .sup .vtt` as external subtitles (`v12.3:Emby.Naming/Common/NamingOptions.cs:162-173`). A format `libse` cannot parse is converted to `.srt` by ffmpeg first (`SubtitleEncoder.cs:250-265`).
2. `GetSubtitleStream` opens it (`SubtitleEncoder.cs:167-209`). See "Text encoding on the pass-through path".
3. **Pass-through**: when the file's format equals the requested one, or the file is SSA and ASS was requested, the stream is returned unchanged (`SubtitleEncoder.cs:139-147`). No start or end trimming happens on this path.
4. **Conversion** otherwise: `SubtitleEditParser` parses it with every `libse` format registered for that extension (`SubtitleEditParser.cs:31-77`), `FilterEvents` trims and shifts times, `TryGetWriter` picks a writer, and the result is `Encoding.UTF8.GetBytes(text)`, so UTF-8 with no BOM (`SubtitleEncoder.cs:77-95`, `:277-321`).

`TryGetWriter` knows six outputs (`SubtitleEncoder.cs:277-321`):

| Requested format | Writer |
| --- | --- |
| `ass` | `libse` `AdvancedSubStationAlpha` |
| `json` (and `js`) | Jellyfin `JsonWriter` |
| `srt`, `subrip` | `libse` `SubRip` |
| `ssa` | `libse` `SubStationAlpha` |
| `vtt`, `webvtt` | `libse` `WebVTT` |
| `ttml` | `libse` `TimedText10` |

### How `Paragraph.Text` holds lines

Every writer except JSON starts from `libse` `Paragraph.Text`. The parsers join the lines of one cue with `Environment.NewLine`: SubRip (`libse:SubtitleFormats/SubRip.cs:243-248`), WebVTT (`libse:SubtitleFormats/WebVTT.cs:310-325`), ASS and SSA turn `\N` and `\n` into it (`libse:SubtitleFormats/AdvancedSubStationAlpha.cs:1729`, `:1813-1816`). `Environment.NewLine` is `\n` on a Linux or macOS server and `\r\n` on a Windows server.

The parsers keep inline markup in `Paragraph.Text` as they found it:

- SubRip keeps `<i>`, `<b>`, `<u>`, `<font ...>`, and ASS-style override blocks such as `{\an8}` verbatim (`SubRip.cs:243-248`; only `\0` is replaced).
- WebVTT keeps cue tags (`<i>`, `<b>`, `<u>`, `<c.x>`, `<v Name>`, `<lang>`, `<ruby>`, inline timestamps), decodes `&lt; &gt; &amp;` (`WebVTT.cs:346-351`, `:1098-1104`), and prepends an `{\anN}` block built from the cue settings to the first line (`WebVTT.cs:289`, `:312`).
- ASS keeps every override block such as `{\i1}`, `{\pos(...)}`, and `\h` (`AdvancedSubStationAlpha.cs:1729`).

## The formats the RTL line rule must handle

The rule runs on what `GetSubtitles` returns. "Line" below means one rendered line inside one cue.

| Output | Path | Where cue text sits | Line separator | Markup that can appear inside a line |
| --- | --- | --- | --- | --- |
| JSON | converted from SRT, VTT, SMI, SUB, TTML, ... | `TrackEvents[i].Text`, a JSON string | `Environment.NewLine` inside the string, escaped as `\n` or `\r\n` | everything the parser kept (list above). Arabic and `< > & ' "` are written as `\uXXXX` escapes |
| WebVTT | converted | the payload lines after each `-->` timing line, up to a blank line | `Environment.NewLine` | `<i> <b> <u> <c.class>`, `<v ...>`, `<font ...>` left over from SRT, `</...>`, entities `&amp; &lt; &gt; &lrm;`. `{\...}` blocks are removed and `{\anN}` becomes a cue setting |
| WebVTT | pass-through (external `.vtt` requested as `vtt`) | cue blocks per the WebVTT spec: optional identifier line, timing line, payload lines up to a blank line; skip `NOTE`, `STYLE`, `REGION` blocks | whatever the file uses: `\r\n`, `\n`, or `\r` | the full WebVTT cue syntax: `<c>`, `<i>`, `<b>`, `<u>`, `<v>`, `<lang>`, `<ruby>`/`<rt>`, `<00:00:01.000>`, any HTML entity such as `&rlm;` or `&nbsp;` |
| SRT | converted | the lines after each `-->` timing line, up to a blank line | `Environment.NewLine` | whatever `Paragraph.Text` holds, unchanged: `<i> <b> <u> <font ...>`, `{\an8}` and other `{\...}` blocks |
| SRT | pass-through (SRT file or embedded track requested as `srt`) | same | whatever the file uses | anything the author wrote, the same tags as above |
| ASS | converted (for example SRT to ASS) | the 10th field of each `Dialogue:` line, after the first 9 commas | the two characters `\N` | `{\i1}{\i0} {\b1}{\b0} {\u1}{\u0} {\fn...} {\fs...} {\c&H...&}` from HTML tags, plus any `{\anN}` or other block the source had |
| SSA | converted | the 10th field of each `Dialogue: Marked=...` line | `\N` | same as ASS |
| TTML | converted | the content of each `<p>` in `<body><div>` | `<br />` elements | `<span tts:fontStyle="italic">`, `tts:fontWeight`, `tts:textDecoration`, `tts:fontFamily`/`tts:color` spans, XML entities |

ASS and SSA files on the pass-through path, including SSA served as ASS, stay out of scope.

Other pass-through pairs exist in theory, because any format `libse` parses passes through when its extension is requested (for example `Stream.smi` for a `.smi` file). No client in this research asks for them. The rule should leave any output format it does not know untouched.

### Markup comes before the first letter

Several of these formats put Latin letters in markup at the start of a line: `{\an8}`, `{\i1}`, `<font color="red">`, `<c.yellow>`, `<v Bob>`. The first-strong-letter test must skip markup, using the markup grammar of each format. In WebVTT, `<v Name>` holds a speaker name that is not shown, so it is markup too.

2
00:00:04,000 --> 00:00:05,500

The writer emits no whitespace. Wrapped here for reading:

{"TrackEvents":[
{"Id":"1","Text":"<i>مرحبا.</i>\nكيف حالك؟","StartPositionTicks":10000000,"EndPositionTicks":30000000},

**WebVTT, converted** (`libse:SubtitleFormats/WebVTT.cs:58-94`). **ASS, converted** (`libse:SubtitleFormats/AdvancedSubStationAlpha.cs:109-264`). Line breaks become `\N` (`:245`), HTML tags become override blocks (`:1001-1080`), and the title is `untitled` (`SubtitleEncoder.cs:91`). The style line is cut short here.

**TTML, converted** (`libse:SubtitleFormats/TimedText10.cs:167-389`, paragraphs at `:429-639`). The lines of one cue are joined with `<br/>` and rebuilt as XML nodes (`:530-546`, `:641-722`). `{\an8}` picks the `topCenter` region (`:477-480`). Times use seconds (`:101-113`). The document goes through `XmlWriter` with `Indent = true` (`libse:SubtitleFormats/SubtitleFormat.cs:509-524`). Head trimmed:

```text
<?xml version="1.0" encoding="utf-8"?>
<tt xmlns="http://www.w3.org/ns/ttml" ... xml:lang="en">
  <head>...</head>
  <body style="s0">
    <div>
      <p begin="1.0s" xml:id="p0" end="3.0s"><span tts:fontStyle="italic">مرحبا.</span><br />كيف حالك؟</p>

```

## Line endings in practice

- Converted SRT, WebVTT, and JSON use `Environment.NewLine` throughout: `\n` on Linux and macOS, `\r\n` on Windows.
- Converted ASS and SSA mix line endings on Linux. The header templates are C# verbatim strings, and the shipped `libse.dll` stores them with `\r\n`: the string after `[V4+ Styles]` in the 12.2 test server's `libse.dll` continues with `\r\nForm`. The `Dialogue` lines are added with `AppendLine`, which writes `\n` on Linux. The cue text itself has no raw line break, only `\N`.
- Converted TTML always uses `\r\n`, because `XmlWriterSettings.NewLineChars` defaults to `\r\n` ([XmlWriterSettings.NewLineChars](https://learn.microsoft.com/dotnet/api/system.xml.xmlwritersettings.newlinechars)). Inside a cue, lines are separated only by `<br />`.
- Pass-through files keep their own line endings.

So the rule must split on `\r\n`, `\n`, and a lone `\r`, and write back the separator it found.

## Text encoding on the pass-through path

`GetSubtitleStream` (`v12.3:MediaBrowser.MediaEncoding/Subtitles/SubtitleEncoder.cs:167-209`):

| Source | What the client gets |
| --- | --- |
| External text file detected as UTF-8 or ASCII, or not detected at all | The raw bytes on disk. A UTF-8 BOM, if present, is kept. |
| External text file in another encoding that .NET supports (UTF-16, Windows-1256, ...) | Decoded and re-encoded as UTF-8 without a BOM. |
| External text file in an encoding .NET cannot decode, such as ISO-8859-16 | 12.3 and 13.0: the raw bytes in that legacy encoding (`:191-197`). 12.0: that branch is missing, so `new StreamReader(stream, null)` throws and the request fails (`git diff v12.0 v12.3`). |
| Embedded track, extracted to the cache | The cache file as ffmpeg wrote it, opened raw with no charset check (`:208`). ffmpeg writes text subtitles as UTF-8. |
| External file converted to `.srt` by ffmpeg first | Charset detection runs again on the new file, so it is treated like the first row. |

The HLS segment endpoint reads the result with a UTF-8 `StreamReader` and writes UTF-8 again (`SubtitleController.cs:249-261`). So a legacy-encoded file still reaches the client as broken text on that path.

The rule should decode with BOM detection, fall back to UTF-8, and leave the stream untouched when the bytes are not valid UTF-8 or UTF-16.

## What clients request

### Jellyfin Web

- **Device profile**: `vtt` External, then `ass` and `ssa` External unless ASS rendering is off, then `pgssub` and `vobsub` when PGS rendering is on (`jellyfin-web:src/scripts/browserDeviceProfile.js:1609-1644`). It has no `Hls` or `Embed` subtitle profile.
- **The server picks a URL per track** (`v12.3:MediaBrowser.Model/Dlna/StreamBuilder.cs:1465-1543`, `:1576-1640`). It first looks for a profile that needs no conversion, then for one that does. Conversion to `ass` or `ssa` is never allowed, and neither is conversion from them (`v12.3:MediaBrowser.Model/Entities/MediaStream.cs:772-804`). So an SRT or VTT track gets `Stream.vtt`, and an ASS or SSA track gets `Stream.ass` or `Stream.ssa` (`v12.3:MediaBrowser.Model/Dlna/StreamInfo.cs:1230-1284`).
- **The player fetches JSON for every text track that is not ASS or SSA.** `fetchSubtitles` swaps `.vtt` for `.js` in the delivery URL (`jellyfin-web:src/plugins/htmlVideoPlayer/plugin.js:168-178`, `:1329-1338`), and both the custom subtitle element and the native `<track>` path use it (`plugin.js:1614-1690`). The player never fetches `Stream.vtt` itself.
- ASS and SSA go to SubtitlesOctopus as `Stream.ass` or `Stream.ssa`, which is pass-through and out of scope (`plugin.js:47-48`, `:1617-1619`).
- `normalizeTrackEventText` turns `\N` into a newline, drops `\r` and `{\...}` blocks, splits on `\n`, and prepends U+200E to each line (`plugin.js:158-166`). The custom element then renders it through `innerHTML`, sanitized with DOMPurify (`plugin.js:1713-1714`).
- `v12.2` and `master` do not differ in any of this.

**Web needs: JSON.**

### HLS

- When a stream is transcoded to HLS and the subtitle method is `Hls` (or the request sets `EnableSubtitlesInManifest`), the master playlist lists **every text subtitle track**, ASS included, as `{mediaSourceId}/Subtitles/{index}/subtitles.m3u8` (`v12.3:Jellyfin.Api/Helpers/DynamicHlsHelper.cs:192-210`, `:675-710`).
- That playlist lists 30-second segments `stream.vtt?CopyTimestamps=true&AddVttTimeMap=true&StartPositionTicks=...&EndPositionTicks=...` (`SubtitleController.cs:337-408`). Each segment calls `GetSubtitles` with `vtt` and adds the timestamp map.
- An external `.vtt` passes through, and pass-through ignores the start and end ticks. So **every segment returns the whole file**.

**HLS needs: WebVTT, converted (from SRT, ASS, SSA, and others) and pass-through (external `.vtt`).**

### Jellyfin iOS app, native player

- With the native player on, the app sends the profile from `utils/profiles` (`jellyfin-ios:components/NativeShellWebView.tsx:55`, `assets/js/plugins/NativeVideoPlayer.staticjs:162-164`). Its only subtitle profile is `{ Format: 'vtt', Method: Hls }` (`jellyfin-ios:utils/profiles/base.ts:108-113`).
- An `Hls` profile only applies to transcodes (`StreamBuilder.cs:1585-1588`). In direct play no profile fits, so the subtitle falls back to `Encode`, which forces a transcode (`StreamBuilder.cs:1320-1330`). Once it transcodes, text tracks other than ASS and SSA get `Hls`. ASS and SSA still find no profile, because conversion from them is refused, so they are burned in.
- With the native player off, the app runs Jellyfin Web in a web view, with Web's own profile (`jellyfin-ios:assets/js/NativeShell.staticjs:71-79`), so it gets JSON.

**iOS native player needs: WebVTT over HLS.**

## What this means for the plan

1. **JSON has to be parsed, not searched.** Arabic arrives as `م...` escapes, so a byte-level find and replace cannot see an RTL letter. The decorator has to deserialize `TrackEvents`, fix each `Text`, and serialize it again with the same four fields.
2. **ASS reaches clients as WebVTT.** The HLS manifest lists ASS tracks too, and `GetSubtitles` converts ASS to WebVTT for them without complaint. The same happens for any request like `Stream.js` on an ASS track. The rule "ASS stays as authored" should therefore be keyed on the **source track's codec** (`ass` or `ssa`), not on the output format. The decorator gets the item, media source id, and stream index, so it can look up the codec.
3. **SRT to ASS never comes from a device profile.** `StreamBuilder` refuses conversion to ASS or SSA. That output only appears for a hand-built URL or a third-party client, so ASS, SSA, and TTML output are low priority next to JSON and WebVTT.
4. **Line breaks vary.** Inside one response you can find `\n`, `\r\n`, `\N`, and `<br />`. The separator depends on the format, the server OS, and the source file.
5. **HLS pass-through is repeated work.** For an external `.vtt`, every 30-second segment carries the whole file, so the decorator fixes the whole file once per segment. Caching the fixed result per file is worth considering.
6. **Remote external subtitles skip the server.** When an external subtitle sits at an `http(s)` URL and needs no conversion, the client is handed that URL directly (`StreamInfo.cs:1263-1274`). This is rare (`.strm` items) and out of reach.
7. **Don't wrap a line twice.** Pass-through files may already carry RLE, RLM, `&rlm;`, or a previous fix. The rule should leave a line alone when it already starts with an embedding or isolate mark.
