## Short answers

- **Jellyfin Web reaches most viewers.** Besides the browser, six official apps show Jellyfin Web in full: the iPhone/iPad app, the Android app, Jellyfin Desktop, webOS, Xbox, and Tizen. All but Tizen load it from the server, so they run whatever Jellyfin Web the server serves. Tizen ships its own copy, so a change to the server's Jellyfin Web files does not reach it. No official client shows Jellyfin Web only in part.
- **Eight official clients never show Jellyfin Web:** seven native ones (Android TV, Swiftfin, Roku, Jellyfin MPV Shim, the Kodi add-on, JellyCon, and Mopidy-Jellyfin) and Jellyfin Vue, which is a separate web app. Only the server route reaches them.
- **The `usersettings` display preferences under client `emby` are the shared settings store.** Jellyfin Web, the Android app's native player, Android TV, Roku, and MPV Shim all read it. Swiftfin, Vue, Kodi, JellyCon, and Mopidy never read it.
- **Next Up, Resume, Latest, and PlaybackInfo reach almost every client.** Every client with a home screen calls the first three, and every client that plays video calls PlaybackInfo. The Kodi add-on is the exception for home rows: it copies the library into Kodi's own database and builds its lists there.
- **Branding reaches clients unevenly.** Branding custom CSS reaches every Jellyfin Web client, Tizen included, and nothing else. The splash screen reaches Jellyfin Web, Android TV, Swiftfin, and Roku. The login disclaimer reaches Jellyfin Web, Android TV, Swiftfin, and Vue.
- **The best server-route mechanism is a global MVC action or result filter**, added by `IPluginServiceRegistrator` through `services.Configure<MvcOptions>`. It sees typed request and response objects after authentication, for every API controller. An `IStartupFilter` middleware also works, but sees raw, possibly compressed bytes before authentication; keep it for traffic MVC never sees, such as Jellyfin Web's static files. Service decoration, as `research/plugin-service-replacement.md` does, fits only small, stable interfaces: `ILibraryManager` gained three members between 12.0 and 12.3, which would stop a 12.0-built decorator from loading.

### Jellyfin Web

- The server serves Jellyfin Web's files from `/web` (`master:Jellyfin.Server/Startup.cs:202-229`) and redirects a bare server address to it (`Jellyfin.Api/Middleware/BaseUrlRedirectionMiddleware.cs:63-72`). So every client that opens the server address runs the server's Jellyfin Web.
- `userSettings.set(name, value, enableOnServer)` writes to `localStorage` through `appSettings` and, unless `enableOnServer` is `false`, also into `CustomPrefs` of `usersettings`/`emby` (`jellyfin-web:src/scripts/settings/userSettings.js:13-15`, `:105-113`; `localStorage` at `jellyfin-web:src/scripts/settings/appSettings.js:265`, `:273`). `get` reads the server copy unless `enableOnServer` is `false` (`jellyfin-web:src/scripts/settings/userSettings.js:128-135`).
- Device-only settings are the ones passed `false`: audio channels, fMP4, cinema mode, theme songs and videos, backdrops, blurhash, custom CSS, language, date locale, theme, screensaver, library page size, and others (`jellyfin-web:src/scripts/settings/userSettings.js:167-527`).
- Server-stored ones include the home sections (`jellyfin-web:src/components/homesections/homesections.js:35`) and `enableNextVideoInfoOverlay` (`jellyfin-web:src/scripts/settings/userSettings.js:233`).
- User configuration, such as audio and subtitle language, is read and written through `serverConfig` and `updateUserConfiguration` (`jellyfin-web:src/scripts/settings/userSettings.js:142-157`).
- Home rows call Next Up and Resume (`jellyfin-web:src/components/homesections/sections/nextUp.ts:29`, `jellyfin-web:src/components/homesections/sections/resume.ts:46`). Playback calls PlaybackInfo (`jellyfin-web:src/components/playback/playbackmanager.js:419`).
- Branding: the admin's custom CSS goes into a `<style>` tag unless the viewer turned it off (`jellyfin-web:src/components/CustomCss.tsx:6-22`); the login page shows the login disclaimer (`jellyfin-web:src/apps/legacy/controllers/session/login/index.js:302-306`); backdrops use the splash screen when it is on (`jellyfin-web:src/scripts/autoBackdrops.js:68-69`).

| Server change | Reaches |
| --- | --- |
| A key in `usersettings`/`emby` `CustomPrefs` | Every Jellyfin Web client, the Android native player, Android TV, Roku, MPV Shim |

## Part 2: how a plugin changes API requests and responses

### Where plugin code runs during startup

1. `Program.StartServer` builds a generic host. Its first `ConfigureServices` callback is `appHost.Init(services)`, and `ConfigureWebHostDefaults` comes after it (`master:Jellyfin.Server/Program.cs:178-183`; the same lines at `v12.0:Jellyfin.Server/Program.cs:170-175`).
2. `Init` registers the core services, then calls `_pluginManager.RegisterServices` (`Emby.Server.Implementations/ApplicationHost.cs:490-492`). That runs every enabled plugin's `IPluginServiceRegistrator.RegisterServices` on the host's own `IServiceCollection` (`Emby.Server.Implementations/Plugins/PluginManager.cs:206-226`).
3. The web host then runs `Startup.ConfigureServices` through `UseStartup(context => new Startup(...))` (`Jellyfin.Server/Extensions/WebHostBuilderExtensions.cs:53`). The factory overload adds its own `ConfigureServices` callback ([GenericWebHostBuilder.cs:191-200](https://github.com/dotnet/aspnetcore/blob/7387de91234d3ef751fa50b3d1bfede4130213ff/src/Hosting/Hosting/src/GenericHost/GenericWebHostBuilder.cs#L191-L200)), and the host runs callbacks in the order they were added ([HostBuilder.cs:97](https://github.com/dotnet/runtime/blob/60629d14374c56f1cb51819049ad1fa529307f8d/src/libraries/Microsoft.Extensions.Hosting/src/HostBuilder.cs#L97), [:346](https://github.com/dotnet/runtime/blob/60629d14374c56f1cb51819049ad1fa529307f8d/src/libraries/Microsoft.Extensions.Hosting/src/HostBuilder.cs#L346)). So plugin registrations land in the same collection, before `AddJellyfinApi`.
4. `AddJellyfinApi` calls `AddMvc`, clears the application parts, adds the API assembly and every assembly that contains a controller, and configures JSON (`Jellyfin.Server/Extensions/ApiServiceCollectionExtensions.cs:111-163`). It adds no global MVC filter.
5. `Startup.Configure` builds the pipeline inside `app.Map(BaseUrl, ...)`: forwarded headers, `ExceptionMiddleware`, response time, WebSockets, response compression, CORS, localization, Jellyfin Web static files, static files, authentication, Swagger, query string decoding, routing, authorization, IP access, the WebSocket handler, the startup message, metrics, then controllers (`master:Jellyfin.Server/Startup.cs:168-259`).

Lazyfin already references `Microsoft.AspNetCore.App` through `Jellyfin.Common` and `Jellyfin.Model` (`frameworkReference` in their 12.0.0 `.nuspec` files), so it can use MVC and hosting types with no new package.

### Option 1: global MVC action and result filters (best)

How: in `RegisterServices`, call `serviceCollection.Configure<MvcOptions>(o => o.Filters.Add<LazyfinApiFilter>())` and register the filter type. Options setups run in registration order, so this runs before Jellyfin's own `AddMvc` setup; that does not matter for `Filters`, but a plugin that wants to change formatters must use `PostConfigure`, because Jellyfin inserts its formatters at index 0 later (`Jellyfin.Server/Extensions/ApiServiceCollectionExtensions.cs:125-126`).

What it can change:

- Every action of every API controller, because all of `Jellyfin.Api` is an application part (`Jellyfin.Server/Extensions/ApiServiceCollectionExtensions.cs:135-136`).
- **On the way in**, an `IAsyncActionFilter` sees the bound, typed arguments after authentication and authorization, and can change them or answer early. Examples: the `PlaybackInfoDto` body of `POST /Items/{itemId}/PlaybackInfo` (`Jellyfin.Api/Controllers/MediaInfoController.cs:116-119`), the `UserConfiguration` of `POST /Users/Configuration` (`Jellyfin.Api/Controllers/UserController.cs:467-471`), or the `DisplayPreferencesDto` of `POST /DisplayPreferences/{id}` (`Jellyfin.Api/Controllers/DisplayPreferencesController.cs:112-115`).
- **On the way out**, a result filter sees the typed value before JSON is written: `QueryResult<BaseItemDto>` from Next Up and Resume (`Jellyfin.Api/Controllers/TvShowsController.cs:75-77`, `Jellyfin.Api/Controllers/ItemsController.cs:921-923`), `IEnumerable<BaseItemDto>` from Latest (`Jellyfin.Api/Controllers/UserLibraryController.cs:527-529`), `PlaybackInfoResponse` (`Jellyfin.Api/Controllers/MediaInfoController.cs:72-75`), `DisplayPreferencesDto` (`Jellyfin.Api/Controllers/DisplayPreferencesController.cs:48-51`), `UserDto` (`Jellyfin.Api/Controllers/UserController.cs:581-585`), and `BrandingOptionsDto` (`Jellyfin.Api/Controllers/BrandingController.cs:30-32`). The DTO types come from `Jellyfin.Model`, which Lazyfin already compiles against.
- Because it runs after authentication, the filter knows the viewer and can act per viewer.

What it cannot change: anything that is not an MVC action. That is Jellyfin Web's static files (`master:Jellyfin.Server/Startup.cs:202-231`), WebSocket traffic (`master:Jellyfin.Server/Startup.cs:189`, `:239`), and `/health` (`master:Jellyfin.Server/Startup.cs:256`). File and stream results, such as images and video, pass through as streams, not typed values.

How it breaks across versions:

- It matches actions by name, such as controller `TvShows` and action `GetNextUp`. `Jellyfin.Api` is not a NuGet package (nuget.org returns 404 for `jellyfin.api`), so a rename compiles fine and silently stops the change. Each supported server version needs a test that the matched actions still exist.
- Legacy routes are separate actions that call the new method directly, so a filter must match both: `GetResumeItemsLegacy` calls `GetResumeItems` (`Jellyfin.Api/Controllers/ItemsController.cs:1027-1047`), and `GetLatestMediaLegacy` calls `GetLatestMedia` (`Jellyfin.Api/Controllers/UserLibraryController.cs:619-635`). Roku and JellyCon use these legacy routes.
- A changed return type or DTO shape breaks the cast. A filter should check the type and pass the result through unchanged when it does not match.
- An exception in the filter fails that request for every client. It reaches `ExceptionMiddleware` (`master:Jellyfin.Server/Startup.cs:185`). The filter should catch its own errors and fall back to Jellyfin's answer.

### Option 2: middleware through an `IStartupFilter`

How: register `IStartupFilter` in `RegisterServices`. `GenericWebHostService` takes every `IStartupFilter` from the container and wraps the startup's `Configure` with them ([GenericWebHostService.cs:27](https://github.com/dotnet/aspnetcore/blob/7387de91234d3ef751fa50b3d1bfede4130213ff/src/Hosting/Hosting/src/GenericHost/GenericWebHostService.cs#L27), [:135-140](https://github.com/dotnet/aspnetcore/blob/7387de91234d3ef751fa50b3d1bfede4130213ff/src/Hosting/Hosting/src/GenericHost/GenericWebHostService.cs#L135-L140)). Jellyfin has no `IStartupFilter` of its own, so Lazyfin's would be the only one unless another plugin adds one.

What it can change: any HTTP request or response, including Jellyfin Web's static files, so it is the server-side way to rewrite `index.html` for the Jellyfin Web route (LAZ-60's question).

What it cannot do well:

- It runs outside everything in `Startup.Configure`: before the base URL map, before `ExceptionMiddleware`, and before authentication and routing. So it sees paths with the base URL still on, does not know the viewer or the endpoint before calling `next`, and its own exceptions skip Jellyfin's error handling.
- It sits outside `UseResponseCompression` (`master:Jellyfin.Server/Startup.cs:191`). A response it wants to edit arrives compressed when the client asked for compression, so it must strip `Accept-Encoding` for the requests it edits, or decompress.
- It edits bytes, not DTOs: it must buffer the body, parse JSON, and write it back, for each casing profile Jellyfin offers (`Jellyfin.Server/Extensions/ApiServiceCollectionExtensions.cs:125-126`).
- A filter cannot put middleware in the middle of Jellyfin's pipeline, only around it.

How it breaks: an `IStartupFilter` is an ASP.NET Core contract, not a Jellyfin one, so it survives Jellyfin changes. What breaks is what it matches on: URL paths and JSON property names.

### Option 3: replacing or decorating server services

How: as `research/plugin-service-replacement.md` does for `ISubtitleEncoder` and `ITranscodeManager`, remove the core descriptor and register a decorator.

What it reaches, by endpoint:

| Endpoint | Service behind it | Fit |
| --- | --- | --- |
| Next Up | `ITVSeriesManager.GetNextUp` (`Jellyfin.Api/Controllers/TvShowsController.cs:102`), two members (`MediaBrowser.Controller/TV/ITVSeriesManager.cs:20`, `:29`) | Good |
| Latest | `IUserViewManager.GetLatestItems` (`Jellyfin.Api/Controllers/UserLibraryController.cs:560`) | Fair |
| Display preferences | `IDisplayPreferencesManager` (`Jellyfin.Api/Controllers/DisplayPreferencesController.cs:63-64`, `:218-220`) | Fair |
| Resume | `ILibraryManager.GetItemsResult` (`Jellyfin.Api/Controllers/ItemsController.cs:978`) | Poor: the interface is huge and grows |
| PlaybackInfo | `MediaInfoHelper` (`Jellyfin.Api/Controllers/MediaInfoController.cs:87`, `:177`), a concrete `Jellyfin.Api` class registered as itself (`Emby.Server.Implementations/ApplicationHost.cs:631`) | Not reachable at compile time; only `IMediaSourceManager` underneath |

What it does well: it changes the result for every caller of the service, not only one endpoint, and it needs no route matching.

How it breaks:

- A decorator compiled against 12.0.0 must implement every interface member. `ILibraryManager` gained `GetNamedViewId`, `GetShadowViewId`, and `GetTagNames` between `v12.0` and `v12.3` (`v12.3:MediaBrowser.Controller/Library/ILibraryManager.cs:493`, `:514`, `:858`). On 12.3 a 12.0-built `ILibraryManager` decorator would fail `GetTypes()` and disable all of Lazyfin, as `research/plugin-service-replacement.md` section 2 explains.
- It changes data for every caller, including other server code and other plugins, which can be more than the change intends.
- It cannot see the HTTP request, so it cannot tell which client asked.

### Recommendation

- Use **MVC filters** for changing API requests and responses. They see typed DTOs, run after authentication, sit inside Jellyfin's error handling and compression, and depend only on action names and `Jellyfin.Model` types.
- Use **service decoration** only where the change belongs to the service for every caller and the interface is small and stable, as the RTL fix does.
- Use an **`IStartupFilter`** only for traffic MVC never sees, such as Jellyfin Web's static files.
- Whatever is chosen, add a test per supported server version that the matched actions and DTO types still exist.

## For the map

Facts the map's "Not yet specified" section could use:

- **Where Lazyfin stores a setting it adds.** A key in `usersettings`/`emby` `CustomPrefs` reaches Jellyfin Web, the Android native player, Android TV, Roku, and MPV Shim with no client change, because they already read that document. Swiftfin, Vue, Kodi, and JellyCon would never see it. A Lazyfin-only document or plugin configuration reaches no client unless Lazyfin also changes what that client reads.
- **Tizen bundles its own Jellyfin Web.** A Jellyfin Web route that changes the server's static files misses Tizen. One that works through API responses, such as branding custom CSS, reaches it. This matters for LAZ-62.
- **Branding custom CSS is a server-route channel into every Jellyfin Web client**, Tizen included, but it carries only CSS, and the viewer can turn it off. Using it also means sharing a field the admin owns.
- **WebSocket messages were not researched.** They carry remote control and some notifications, and none of the three mechanisms above changes them.

Tickets the map could add:

- A prototype that proves a global MVC filter can rewrite Next Up and `PlaybackInfo` on 12.2 and 13.0, including the legacy routes, with a test that fails when an action is renamed.
- A research ticket on whether the server route can tell clients apart (the `Authorization` header's client name and device ID), so a change can target only native clients or only Jellyfin Web.
