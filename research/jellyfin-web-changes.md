## Short answer

A plugin has one clean way to change the Jellyfin Web code every viewer runs: register an ASP.NET Core `IStartupFilter` that adds a middleware. The middleware rewrites the server's response for `/web/index.html` to add one `<script>` tag, and Lazyfin serves that script from its own controller. Both JavaScript Injector and File Transformation do exactly this today. It needs no setup, no other plugin, no disk write, and no server internals, and it works the same on 12.0, 12.3, and 13.0 `master`. It reaches every browser and both official phone apps, because both apps load Jellyfin Web from the server.

The other ways are worse. Writing to the web folder on disk fails in the official Docker image and Debian package, and is undone by every update. Harmony patching breaks with server changes. Shipping a patched Jellyfin Web build must match every Jellyfin Web release. The server's own hooks, branding custom CSS and plugin configuration pages, are either CSS only and owned by the admin, or only reach the admin dashboard.

Rule 4 is the hard part. Jellyfin maintainers rejected a server API for this exact purpose and said plugins should not change Jellyfin Web. So the injection itself will never move upstream. What can move upstream is each enhancement, if Lazyfin writes it as Jellyfin Web code that plugs into Jellyfin Web's own seams, not as DOM patches.

## How the server serves Jellyfin Web

These facts decide what each way can hook into.

- **Jellyfin Web is a folder of static files.** When `hostwebclient` is on, which is the default, the server serves `ApplicationPaths.WebPath` at `/web` with `UseDefaultFiles` and `UseStaticFiles` (`server-master:Jellyfin.Server/Startup.cs:202-226`, `server-12.0:...:200-224`; default on at `server-master:Emby.Server.Implementations/ConfigurationOptions.cs:16`). `/` redirects to `web/` (`ConfigurationOptions.cs:17`, `server-master:Jellyfin.Api/Middleware/BaseUrlRedirectionMiddleware.cs:68`).
- **`index.html` is never cached without a check.** The static file handler sets `Cache-Control: no-cache` on `index.html` only (`server-master:Jellyfin.Server/Startup.cs:219-225`, `server-12.0:...:217-223`). Every page load asks the server again.
- **The web folder location is fixed at startup.** It comes from `--webdir`, then `JELLYFIN_WEB_DIR`, then `<app>/jellyfin-web` (`server-master:Jellyfin.Server/Helpers/StartupHelpers.cs:119-122`). A plugin cannot change it.
- **The pipeline is hard-coded.** `Startup.Configure` builds the middleware list in a fixed order, starting with `UseBaseUrlRedirection` and `Map(config.BaseUrl, ...)`, then response compression, then the web files (`server-master:Jellyfin.Server/Startup.cs:173-226`). There is no plugin hook inside it.
- **Plugin services go into the web host's container.** `Program.cs` builds the host with `.ConfigureServices(services => appHost.Init(services))` (`server-master:Jellyfin.Server/Program.cs:180`, `server-12.0:...:172`). `Init` registers core services, then every enabled plugin's `IPluginServiceRegistrator` (`server-master:Emby.Server.Implementations/ApplicationHost.cs:490-492`, `server-master:Emby.Server.Implementations/Plugins/PluginManager.cs:206-226`). A disabled plugin registers nothing (`PluginManager.cs:218`).
- **ASP.NET Core runs every `IStartupFilter` in that container around `Startup.Configure`.** `GenericWebHostService` takes `IEnumerable<IStartupFilter>` and wraps the app's configure delegate with each one (`aspnetcore:src/Hosting/Hosting/src/GenericHost/GenericWebHostService.cs:27`, `:135-137`). So a filter a plugin registers can add middleware before Jellyfin's whole pipeline.
- **Lazyfin already has the types.** The `Jellyfin.Common` 12.0.0 package that `Jellyfin.Controller` pulls in carries a framework reference to `Microsoft.AspNetCore.App` (`~/.nuget/packages/jellyfin.common/12.0.0/jellyfin.common.nuspec:18`; source at `server-master:MediaBrowser.Common/MediaBrowser.Common.csproj:17`). `IStartupFilter` lives there. No new package is needed.
- **Plugins can serve their own files.** The server adds every assembly that holds an MVC controller to the API (`server-master:Emby.Server.Implementations/ApplicationHost.cs:1010-1015`, used at `server-master:Jellyfin.Server/Startup.cs:73`). Lazyfin can serve its script from a route like `/Lazyfin/...`.
- **No Content-Security-Policy.** A search for `Content-Security-Policy` finds nothing in the server or in Jellyfin Web. `index.html` has no CSP meta tag (`web-master:src/index.html:1-94`).

How Jellyfin Web starts, which decides where a script must go:

- The built `index.html` loads the main bundle with a deferred `<script>` in `<head>`. Jellyfin Web uses `HtmlWebpackPlugin` with defaults for placement (`web-master:webpack.common.js:69-78`), and those defaults are `inject: "head"` and `scriptLoading: "defer"` (`hwp:index.js:138-139`).
- The bundle is `main.jellyfin.bundle.js`, but lazy chunks are named `[name].[contenthash].chunk.js` (`web-master:webpack.common.js:122-125`). Chunk names change with every build.
- At boot, Jellyfin Web reads `config.json` from the server with `cache: 'no-store'` (`web-master:src/scripts/settings/webSettings.js:6-25`) and loads every name in its `plugins` list (`web-master:src/index.jsx:151-177`, `web-12.0:src/index.jsx:142`).
- A plugin name that exists on `window` is loaded from there. Jellyfin Web calls `window[name]()` to get a class, and builds it with `Events`, `loading`, `appSettings`, `playbackManager`, `globalize`, `appHost`, `appRouter`, `inputManager`, `toast`, `confirm`, `dashboard`, and `ServerConnections` (`web-master:src/components/pluginManager.js:63-93`). Any other name must be a file bundled in Jellyfin Web (`pluginManager.js:97`). Any plugin type is accepted (`pluginManager.js:32-61`).
- The native apps add their own names from `window.NativeShell.getPlugins()` (`web-master:src/index.jsx:166-168`).

## The ways

### Way 1: Rewrite files in the web folder on disk

The plugin opens `WebPath/index.html` and writes a `<script>` tag into it. JavaScript Injector did this before it moved to middleware, and still does it as a fallback: `InjectScript` reads `index.html`, adds its block before `</body>`, and calls `File.WriteAllText` (`jsi:Jellyfin.Plugin.JavaScriptInjector/Plugin.cs:37-70`). It runs only when the admin turns the middleware off (`jsi:Jellyfin.Plugin.JavaScriptInjector/Services/StartupService.cs:44-49`, `jsi:.../Configuration/PluginConfiguration.cs:37`). The upstream PR discussion names Jellyscrub as another plugin that edited `index.html` on disk ([jellyfin#9095 comment](https://github.com/jellyfin/jellyfin/pull/9095#issuecomment-1383122450)).

Where it breaks:

- **Official Docker image.** The web folder is copied into the image at `/jellyfin/jellyfin-web` (`packaging:docker/Dockerfile:134`, `:252`). Only the data and cache folders are volumes, and only they are made writable (`packaging:docker/Dockerfile:249`, `:262`). The web folder belongs to root. If the container runs as a non-root user, the write fails. If it runs as root, the write lands in the container layer and is gone when the admin pulls a new image.
- **Debian and Ubuntu packages.** The web files live in `/usr/share/jellyfin/web` (`packaging:debian/conf/jellyfin:28`), installed by the `jellyfin-web` package, and the server runs as the `jellyfin` system user (`packaging:debian/jellyfin-server.postinst:12`, `:30`). That user cannot write there. A package upgrade replaces the files.
- **Every Jellyfin update** replaces `index.html`, so the plugin must notice and write again at each start.
- **A separately hosted web client.** If the admin turns `hostwebclient` off, the server has no web folder to write (`server-master:Jellyfin.Server/Program.cs:120-131`, `:394`).

### Way 2: Rewrite responses with middleware, added through `IStartupFilter`

The plugin registers an `IStartupFilter` in its `IPluginServiceRegistrator`. The filter adds a middleware before Jellyfin's pipeline. For a request to `/web/`, `/web`, or `/web/index.html`, the middleware lets Jellyfin answer into a buffer, then adds a `<script>` tag to the HTML and sends it on. The file on disk never changes. This is how JavaScript Injector and File Transformation work today (next section).

Details any version of this must get right, all taken from the two plugins:

- **Run outermost.** The filter adds its middleware and then calls `next(app)`, so it runs before `UseBaseUrlRedirection` and `Map(BaseUrl)` (`jsi:.../Services/ScriptInjectionStartupFilter.cs:43-53`, `ft:.../Infrastructure/FileTransformationStartupFilter.cs:16-25`). The request path therefore still has the admin's base URL in front, so match the end of the path, not the start (`jsi:.../ScriptInjectionStartupFilter.cs:161-171`, `ft:.../Infrastructure/FileTransformationMiddleware.cs:31-45`).
- **Ask for plain bytes.** Jellyfin compresses responses (`server-master:Jellyfin.Server/Startup.cs:191`). Both plugins remove `Accept-Encoding` from the request so the HTML comes back uncompressed (`jsi:.../ScriptInjectionStartupFilter.cs:83`, `ft:.../FileTransformationMiddleware.cs:57-61`). JavaScript Injector also removes `Range` and `If-Range` (`jsi:...:84-85`).
- **Only rewrite a full 200 HTML answer.** Pass 304s, redirects, and errors through unchanged (`jsi:...:108-116`, `ft:...:94-100`).
- **Fix the headers.** The body changed, so `Content-Length` must be set again and the file's `ETag` and `Last-Modified` must go (`jsi:...:146-155`). File Transformation instead computes a new `ETag` from the changed bytes and answers its own 304s (`ft:...:130-153`).
- **Never break the page.** On any error, serve the original HTML (`jsi:...:140-144`, `ft:...:103-117`).

Where it breaks:

- **Stale browser caches after install (found in the code, not tested).** Before Lazyfin is installed, a browser caches `index.html` with the file's `ETag`. After install, it asks again with `If-None-Match`. ASP.NET Core's static file handler compares that to the file's `ETag` and answers 304 (`aspnetcore:src/Middleware/StaticFiles/src/StaticFileContext.cs:163-171`, `:335-337`). Both plugins pass a 304 through untouched, so that browser keeps the old page with no script, until the web files change in a Jellyfin update. The fix is to also strip `If-None-Match` and `If-Modified-Since` from `index.html` requests before calling the rest of the pipeline, then do your own `ETag` check like File Transformation does.
- **A separately hosted web client.** If the admin serves Jellyfin Web from somewhere else and turns `hostwebclient` off (`server-master:Jellyfin.Server/Startup.cs:202`), no `index.html` passes through the server. Nothing reaches those viewers.
- **A reverse proxy that adds a strict CSP.** Jellyfin sets none, but an admin's proxy could send `script-src 'self'`. An external script served by Lazyfin from the same server passes that. An inline `<script>` block, like JavaScript Injector's private loader (`jsi:.../Helpers/JavascriptHelper.cs:19-48`), would be blocked. So Lazyfin should inject only `<script src>` tags.
- **The service worker does not get in the way.** Jellyfin Web's service worker only handles notification clicks and has no `fetch` handler, so it caches nothing (`web-master:src/serviceworker.js:20-38`). It is also not registered inside the Android app (`web-master:src/index.jsx:204-213`).
- **Another plugin doing the same.** JavaScript Injector and File Transformation can run beside Lazyfin. Each filter wraps the next and each reads the HTML the inner one produced, so the edits stack. Each must stay idempotent.
- **Where in the page the script goes.** JavaScript Injector puts its tags before `</body>` (`jsi:...:127-132`). That runs after the main bundle, which is deferred in `<head>`. A script that must exist before Jellyfin Web loads its plugins should go in `<head>`, before the main bundle's tag.

### Way 3: Patch the server at runtime with Harmony

Harmony rewrites a .NET method in memory. File Transformation used it until April 2026: it patched `Jellyfin.Server.Startup.Configure` with a prefix and replaced it with its own copy of the method, swapping in its own file provider for `/web` (`ft-harmony:src/Jellyfin.Plugin.FileTransformation/Helpers/PatchHelper.cs:8-19`, `ft-harmony:src/Jellyfin.Plugin.FileTransformation/Helpers/StartupHelper.cs:43`, `:114-121`). The copy had to be kept per Jellyfin version, in `JellyfinVersionSpecific/10.10.7` and `JellyfinVersionSpecific/10.11`. The author replaced all of it with an `IStartupFilter` in [`5db73e04`](https://github.com/IAmParadox27/jellyfin-plugin-file-transformation/commit/5db73e04d3129a0d792640c5c8d1c9580662cbe9) ("Replaced Harmony with IStartupFilter middleware").

Where it breaks: any change to the patched server method. It needs the Harmony library shipped in the plugin. It can never move upstream. Way 2 does the same job with public APIs, so there is no reason to use this.

### Way 4: Serve a patched Jellyfin Web build

Lazyfin could ship its own Jellyfin Web build, with its changes made in the Jellyfin Web source, and have a Way 2 middleware serve those files instead of the ones in `WebPath`. A lighter form rewrites single bundle files.

Where it breaks: Jellyfin Web is released with the server, and Lazyfin supports every 12.x. A shipped build must match each server version, and it overrides fixes the admin gets from a Jellyfin update until Lazyfin releases again. Rewriting single files is worse: chunk names carry a content hash that changes every build (`web-master:webpack.common.js:125`), and the code is minified. Its one strength is rule 4: each change is a real Jellyfin Web source change, ready to send upstream.

### Way 5: Branding custom CSS (built into the server)

The server stores `BrandingOptions.CustomCss`, which the admin sets in the dashboard (`server-master:MediaBrowser.Model/Branding/BrandingOptions.cs:18`), and returns it from `/Branding/Configuration` and `/Branding/Css` (`server-master:Jellyfin.Api/Controllers/BrandingController.cs:30-64`). Jellyfin Web puts it in a `<style>` tag (`web-master:src/components/CustomCss.tsx:12-16`) on the main and legacy layouts (`web-master:src/apps/modern/AppLayout.tsx:79`, `web-master:src/apps/legacy/AppLayout.tsx:15`).

How far it reaches: CSS only. It cannot run code. Each viewer can switch it off in their display settings (`CustomCss.tsx:12`, `web-master:src/components/displaySettings/displaySettings.js:133`). It is one text field that belongs to the admin, so a plugin that writes to it overwrites the admin's own CSS. The login disclaimer next to it is sanitized with DOMPurify, so it cannot run script either (`web-master:src/apps/legacy/controllers/session/login/index.js:306`).

### Way 6: Plugin configuration pages (built into the server)

A plugin that implements `IHasWebPages` lists HTML and JavaScript files embedded in its assembly. Each `PluginPageInfo` can ask for a menu entry with `EnableInMainMenu`, `MenuSection`, and `MenuIcon` (`server-master:MediaBrowser.Model/Plugins/PluginPageInfo.cs:26-36`). The server serves them at `/web/ConfigurationPage?name=...` (`server-master:Jellyfin.Api/Controllers/DashboardController.cs:73-93`). Jellyfin Web imports a page's controller script only when that page opens (`web-master:src/components/viewContainer.js:19-28`).

How far it reaches: only the admin dashboard. The list of pages needs an admin login (`DashboardController.cs:49-50`), and the script runs only on that page. It is the right place for Lazyfin's own settings page, not for changing what viewers see.

### Not a way on its own: Jellyfin Web's plugin API

Jellyfin Web loads plugins named in `config.json`, and a name found on `window` is built with Jellyfin Web's core services (see "How the server serves Jellyfin Web"). Both official phone apps use this: the iOS app adds `NativeAudioPlayer` and `NativeVideoPlayer` (`ios:assets/js/NativeShell.staticjs:106-111`), and the Android app adds `NavigationPlugin`, `ExoPlayerPlugin`, `ExternalPlayerPlugin`, and `MediaSegmentsPlugin` (`android:app/src/main/assets/native/nativeshell.js:19-24`, `:82-84`).

A Way 2 middleware can use it. It adds the name `LazyfinPlugin` to the `plugins` list in the `/web/config.json` response, and puts a script in `<head>` that sets `window.LazyfinPlugin`. Jellyfin Web then hands Lazyfin `playbackManager`, `appRouter`, `Events`, and the rest, with no DOM scraping. Rewriting the response also leaves the admin's own `config.json` alone; on Debian that file is a config file the admin may have edited (`packaging:debian/jellyfin-web.conffiles:1`). This is the closest thing Jellyfin Web has to a public extension point, so it is the best place to hang enhancements that should later move upstream.

## How JavaScript Injector and File Transformation do it

Both are Way 2 today. Lazyfin can do the same in about one class and one middleware, with no dependency on either.

**JavaScript Injector** registers `ScriptInjectionStartupFilter` as a singleton `IStartupFilter` (`jsi:Jellyfin.Plugin.JavaScriptInjector/PluginServiceRegistrator.cs:21`). It moved to this in [`8fe6df62`](https://github.com/n00bcodr/Jellyfin-JavaScript-Injector/commit/8fe6df620fedf72cd3edd04ff970e5fe3e3f5004) ("Add Jellyfin 12 support via IStartupFilter, drop 10.10.7"). Its own docs say it replaced the File Transformation dependency and the on-disk write that failed on Docker (`jsi:.../Services/ScriptInjectionStartupFilter.cs:13-32`). The middleware handles only GET requests for `index.html` (`:57-70`), and injects a block before `</body>` (`:127-132`). The block is a deferred `<script src="../JavaScriptInjector/public.js?v=<ticks>">` for everyone, plus an inline loader that waits for a login and then fetches `private.js` through `ApiClient` (`jsi:.../Helpers/JavascriptHelper.cs:16-48`). Both scripts come from the plugin's own controller: `public.js` allows anonymous access and `private.js` needs a login (`jsi:.../Controllers/CustomJavaScriptController.cs:92-95`, `:110-113`). The on-disk write and File Transformation are only fallbacks behind a setting (`jsi:.../Services/StartupService.cs:44-49`).

**File Transformation** registers `FileTransformationStartupFilter` as an `IStartupFilter` (`ft:src/Jellyfin.Plugin.FileTransformation/PluginServiceRegistrator.cs:14`). Its middleware is general: other plugins register a regex for a file name under `/web/` and a callback that rewrites the bytes (`ft:.../Infrastructure/FileTransformationMiddleware.cs:47-53`, `:109`). It can also create files that do not exist on disk by turning a 404 into a 200 (`:76-93`). It sets its own `ETag`, answers 304s itself, and compresses the result again with Brotli or gzip (`:130-226`). Other plugins cannot reference it directly because each plugin loads in its own load context, so they find its assembly at runtime and call `PluginInterface.RegisterTransformation` by reflection with a JSON payload (`ft:README.md`, "Referencing this as a library"; `ft:src/Jellyfin.Plugin.FileTransformation/PluginInterface.cs:13-34`). It credits [jellyfin/jellyfin#9095](https://github.com/jellyfin/jellyfin/pull/9095) for the idea.

**What upstream said.** PR #9095 proposed this as a server API in 2023. Maintainers closed it unmerged. One said Jellyfin does not support changes to Jellyfin Web and "should not make it easier to do it in an 'official' way" ([comment](https://github.com/jellyfin/jellyfin/pull/9095#issuecomment-1383107539)). Another reason given: such changes do not reach clients that do not use Jellyfin Web, such as Android TV ([comment](https://github.com/jellyfin/jellyfin/pull/9095#issuecomment-1383215597)). So the injection step itself will not move upstream.

## The official phone apps

Both load Jellyfin Web from the server, so a Way 2 change reaches them.

- **iPhone and iPad.** The app opens a `WebView` at the server's URL (`ios:components/NativeShellWebView.tsx:212`), which is the address the viewer typed with a trailing `/` (`ios:utils/ServerValidator.js:48-66`). The server redirects that to `web/`. The app adds its own scripts before the page loads (`ios:components/NativeShellWebView.tsx:42-79`, `:215`). Lazyfin's script runs beside them.
- **Android.** The app opens the server's URL in a `WebView` (`android:app/src/main/java/org/jellyfin/mobile/webapp/WebViewFragment.kt:193`). It does not touch `index.html`. It swaps the first request for `main.*.bundle.js` with its own loader, which then loads the real bundle with `?deferred=true` (`android:app/src/main/java/org/jellyfin/mobile/webapp/JellyfinWebViewClient.kt:47-49`, `android:app/src/main/assets/native/injectionScript.js`). It also serves any path that contains `/native/` from the app's own files (`JellyfinWebViewClient.kt:52`). So Lazyfin must not put `/native/` in any of its script URLs, or the Android app will never ask the server for them.
- **Native players skip Jellyfin Web's player.** Both apps can play media in a native player (`ios:components/NativeShellWebView.tsx:50-53`, `android:.../WebViewFragment.kt:189`). When they do, a Jellyfin Web change to the video player or subtitle display does not show. Which client shows what is LAZ-61's question.

## Comparison

| Way | 1. Admin sets nothing up | 2. Survives Jellyfin updates | 3. No other plugin | 4. Each change could move upstream |
| --- | --- | --- | --- | --- |
| 1. Rewrite web files on disk | No. Fails in the official Docker image and Debian package unless the admin opens up the web folder | No. Every update and every new Docker image wipes it | Yes | Mechanism no. The script's code depends on how it is written |
| 2. `IStartupFilter` middleware | Yes | Yes. Uses only ASP.NET Core public APIs and the `/web` route, both unchanged from 12.0 to 13.0 | Yes | Mechanism no, upstream refused it. Each enhancement yes, if written as Jellyfin Web code on its plugin API |
| 3. Harmony patch | Yes | No. Tied to private server methods, needed a copy per version | Needs Harmony library | No |
| 4. Patched Jellyfin Web build | Yes | No. Must match every Jellyfin Web release | Yes | Yes, each change is a real Jellyfin Web diff |
| 5. Branding custom CSS | No. It is the admin's own field, and viewers can switch it off | Yes | Yes | CSS only |
| 6. Plugin configuration pages | Yes | Yes | Yes | Reaches only the admin dashboard |

## Recommendation

Use Way 2, built into Lazyfin, with no dependency on JavaScript Injector or File Transformation:

1. Register one `IStartupFilter` in Lazyfin's existing `PluginServiceRegistrator`.
2. Its middleware handles GET requests whose path ends in `/web`, `/web/`, or `/web/index.html`. It removes `Accept-Encoding`, `Range`, `If-Range`, `If-None-Match`, and `If-Modified-Since` before calling the rest of the pipeline, rewrites only a 200 HTML answer, sets its own `ETag` from the new bytes, keeps `Cache-Control: no-cache`, and falls back to the original HTML on any error.
3. It adds one external `<script src>` tag in `<head>`, before the main bundle. No inline script, so a strict CSP on a proxy still allows it.
4. A Lazyfin controller serves that script from a route without `/native/` in it, with a version in the URL for cache busting.
5. The script registers Lazyfin as a Jellyfin Web plugin on `window`, and the middleware adds its name to the `/web/config.json` response. Enhancements then use the services Jellyfin Web hands to plugins. DOM patching is the last resort.
6. Each enhancement is written as if it were a Jellyfin Web pull request: same language, same style, one module per enhancement. That keeps rule 4 true for the changes, even though the loader itself stays Lazyfin's.

## For the map
